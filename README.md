# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 십자가(Cross)인지 X인지 판정하는 Python 콘솔 프로그램입니다.
NPU가 필터와 입력을 "같은 자리끼리 곱해서 전부 더하는" 방식으로 모양을 알아보는 원리를, 외부 라이브러리 없이 반복문으로 직접 구현했습니다.

## 실행 방법

```bash
python main.py
```

- 필요한 것: Python 3.8 이상(개발은 3.12.10, 3.8 도커에서 같은 판정 확인). 외부 라이브러리 없음(NumPy 미사용).
- `data.json`은 `main.py`와 같은 폴더에 둡니다.
- 시작하면 모드를 고릅니다.

| 입력 | 모드 | 하는 일 |
|---|---|---|
| `1` | 사용자 입력(3×3) | 필터 A, 필터 B, 패턴을 3줄씩 입력 → 저장 확인 → MAC 점수 → 판정(A / B / 판정 불가) → 3×3 연산 시간 |
| `2` | `data.json` 분석 | 필터 로드 → 케이스별 MAC · 판정 · expected와 비교(PASS/FAIL) → 크기별 성능 표 → 총/통과/실패 요약 |
| `3` | 패턴 생성기(보너스) | 크기 N을 넣으면 Cross / X 패턴을 만들어 보여 줌 |

- 모드 1에서 행/열 수가 다르거나 숫자가 아닌 값을 넣으면 안내 후 그 줄부터 다시 입력받습니다.
- 모드 2는 케이스 하나가 잘못돼도(필터 크기 불일치, 모양이 깨진 패턴 등) 그 케이스만 FAIL로 기록하고 다음 케이스를 계속 처리합니다.
- 오류 입력 시험: `python tests/check_errors.py` (39건. 스크립트가 main.py를 임시 폴더에 복사해서 돌리므로 저장소의 data.json은 바뀌지 않습니다).

## 구현 요약

- **`Matrix`**: n×n 2차원 배열을 담고 값 읽기/쓰기를 합니다. 3, 5, 13, 25(그 밖의 크기도) 처리합니다.
- **라벨 정규화**: `data.json`의 `expected`에는 `+`, `x`, `cross`, `X`, `Cross`처럼 표기가 섞여 있습니다. 소문자로 바꾼 뒤 `+`/`cross` → `Cross`, `x` → `X` 두 가지로 통일해서 비교합니다.
- **MAC**: 이중 반복문으로 `score += a[r][c] * b[r][c]`를 N²번 합니다. 합계는 일부러 `+=`로 쌓습니다. Python 3.12의 내장 `sum()`은 float 오차를 보정해서, 실제 칩의 누적기처럼 오차가 쌓이는 모습이 가려지기 때문입니다.
- **동점 처리(epsilon)**: 두 필터의 점수 차이 `abs(a - b) < 1e-9`이면 대소를 가리지 않고 `UNDECIDED`(판정 불가)로 둡니다. 이때 expected와 비교하면 FAIL입니다.
- **성능 측정**: 입출력 시간은 빼고 `mac()` 호출 구간만 `time.perf_counter()`로 잽니다. 측정 전에 20번 미리 돌려(warm-up) 버리고, 10번의 평균을 ms로 냅니다.
- **보너스 2개**: ① 2차원 배열을 길이 N²의 1차원 배열로 펴서 MAC한 전/후 비교(성능 표 아래에 같이 출력) ② 크기 N을 넣으면 Cross/X 패턴을 만드는 생성기(메뉴 3번, 모드 1에서 `cross`/`x`로도 사용).

## 결과 리포트

### 1. `data.json` 분석 결과

실행 결과는 **총 6개, 통과 3개, 실패 3개**입니다.

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

### 2. 실패 원인 분석

1. 실패 3건(`size_5_1`, `size_13_2`, `size_25_1`)은 모두 **두 점수가 사실상 같아서 생긴 동점**입니다. 점수 차이는 각각 1.11e-16, 2.66e-15, 1.78e-15입니다.
2. 원인은 라벨 정규화나 스키마 문제가 아닙니다. `expected`는 `Cross`/`X`로 정상 정규화됐고, 필터·패턴 크기도 모두 맞았습니다.
3. 원인은 **부동소수점 오차**입니다. 0.1처럼 2진수로 정확히 표현되지 않는 수를 여러 번 더하면, 수학적으로는 같은 합이 0.9와 0.8999999999999999처럼 끝자리에서 어긋납니다. 두 필터의 가중치가 수학적으로 같은 점수를 만들도록 짜여 있어서(예: `size_5_1`은 Cross 필터 가운데 한 칸 0.9와 X 필터 아홉 칸 × 0.1이 같은 합), 데이터가 일부러 동점을 만들도록 설계된 것으로 보입니다.
4. **epsilon을 빼고 `>`로만 비교해 보면** 세 케이스가 `size_5_1` → Cross, `size_13_2` → X, `size_25_1` → Cross로 판정됩니다. 셋 다 expected와 **반대**입니다. FAIL 수(3)는 같지만, "판정 불가"여야 할 것이 "자신 있게 틀린 답"으로 바뀝니다. 오차 때문에 한쪽이 이기는 것은 정보가 아니라 우연이므로, `1e-9` 안쪽 차이는 동점으로 두는 정책이 맞다고 판단했습니다.
5. 그래서 이 FAIL은 버그가 아니라 **"동점 규칙대로 판정 불가를 정확히 돌려준 결과"**입니다. expected가 정해진 값이라 비교에서는 FAIL로 표시됩니다. 3건을 PASS로 바꾸려면 동점을 임의로 한쪽에 주는 규칙이 필요한데, 그건 과제의 동점 정책과 어긋납니다.
6. 참고로 합계를 내장 `sum()`으로 구하면 Python 3.12가 오차를 보정해 0.9를 내놓기 때문에 점수 모양이 달라 보입니다. 이 프로젝트는 `+=` 누적으로 구현했고, Python 3.8에서도 같은 3 PASS · 3 FAIL이 나옴을 확인했습니다.

### 3. 성능 표

Python 3.12.10, Windows 11 노트북. 크기마다 "10번 평균"을 9번 구해 **중앙값**을 적었습니다(한 번의 평균은 가끔 튀는 값에 흔들립니다. 25×25를 다섯 번 쟀을 때 한 번만 평소의 3배가 나온 적이 있습니다). 입력은 같은 크기의 생성한 Cross 패턴 × X 필터입니다.

| 크기(N×N) | 평균 시간(ms) | 연산 횟수(N²) | 한 칸당 시간(ns) | 3×3 대비 시간 | 3×3 대비 N² |
|---|---|---|---|---|---|
| 3×3 | 0.00051 | 9 | 57 | 1.0배 | 1.0배 |
| 5×5 | 0.00107 | 25 | 43 | 2.1배 | 2.8배 |
| 13×13 | 0.00540 | 169 | 32 | 10.6배 | 18.8배 |
| 25×25 | 0.01802 | 625 | 29 | 35.3배 | 69.4배 |
| 51×51 | 0.07267 | 2,601 | 28 | 142.5배 | 289배 |
| 101×101 | 0.26887 | 10,201 | 26 | 527배 | 1,133배 |
| 201×201 | 1.01475 | 40,401 | 25 | 1,990배 | 4,489배 |

(3·5·13·25는 과제 기준 크기이고, 51 이상은 증가 모양을 보려고 더한 크기입니다. 프로그램의 성능 표에는 과제 기준 4개가 나옵니다.)

### 4. 시간 복잡도 분석: O(N²) 근거

1. `mac()`은 `for r` × `for c`의 이중 반복문이라 곱셈·덧셈이 정확히 N²번 일어납니다. 입력이 N배가 되면 일이 N²배가 되는 것이 O(N²)입니다.
2. 측정 결과에서 **큰 크기끼리는 시간이 N²를 따라갑니다**. 101→201은 N²가 3.96배인데 시간은 3.77배, 51→101은 N²가 3.91배인데 시간은 3.70배입니다. N이 두 배면 시간은 약 네 배입니다.
3. 반대로 **작은 크기에서는 시간이 N²보다 덜 늘어납니다**. 3×3 → 25×25는 N²가 69배인데 시간은 35배입니다. 이유는 칸 수와 상관없이 드는 고정 비용(함수 호출, 변수 준비, 반복문 시작)이 작은 크기에서는 전체의 큰 몫을 차지하기 때문입니다.
4. 이것은 "한 칸당 시간" 열로 확인됩니다. 3×3에서는 57ns인데 N이 커질수록 43 → 32 → 29 → 28 → 26 → 25ns로 줄다가 **약 25ns 근처에서 거의 일정**해집니다. 한 칸당 시간이 일정하다는 것은 총 시간이 칸 수(N²)에 비례한다는 뜻이므로 O(N²)의 근거가 됩니다.
5. 식으로 쓰면 `T(N) ≈ 고정 비용 + (약 25ns) × N²`입니다. 측정된 N이 작을 때는 첫 항이, 클 때는 둘째 항이 모양을 정합니다.
6. 실제 NPU는 이 N²번의 곱셈을 한 번에 병렬로 처리합니다. 이 프로그램은 CPU에서 한 칸씩 순서대로 하므로, N이 커질 때 시간이 N²로 늘어나는 것이 그대로 드러납니다.

### 5. 보너스: 2차원 vs 1차원 배열

같은 입력, 같은 방식(10회 평균, 9회 중앙값)으로 `mac_flat()`을 재서 1차원 시간 ÷ 2차원 시간을 구했습니다. 1차원 배열로 펴는 시간(`flatten`)은 연산 구간 밖이라 포함하지 않았습니다.

| 크기 | 2차원(ms) | 1차원(ms) | 1차원/2차원 |
|---|---|---|---|
| 3×3 | 0.00051 | 0.00029 | 0.57 |
| 5×5 | 0.00107 | 0.00058 | 0.54 |
| 13×13 | 0.00540 | 0.00325 | 0.60 |
| 25×25 | 0.01802 | 0.01311 | 0.73 |
| 51×51 | 0.07267 | 0.05867 | 0.81 |
| 101×101 | 0.26887 | 0.23526 | 0.87 |
| 201×201 | 1.01475 | 0.93436 | 0.92 |

- 1차원이 항상 빠르지만(0.54~0.92배), **이득은 크기가 커질수록 줄어듭니다**. 한 칸을 읽을 때 `a[r][c]`는 인덱싱을 두 번, `a[i]`는 한 번 하는 차이는 칸마다 똑같이 생기는데, 2차원은 행마다 안쪽 반복문을 새로 시작하는 비용이 따로 듭니다. 작은 N에서는 행당 비용이 전체에서 차지하는 비중이 크고(N이 작을수록 행당 칸 수가 적으므로), 큰 N에서는 칸마다 드는 일이 전체를 정해서 차이가 줄어드는 것으로 보입니다(추정이며 따로 검증하지는 않았습니다).
- 두 방식 모두 N² 증가 모양은 같으므로 복잡도 등급은 O(N²)로 변하지 않고, 상수만 달라집니다.
